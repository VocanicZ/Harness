# A change to what I asked for

I have been using the first version of this and I want three things changed. Everything else stays as I described it.

## 1. Round half to even

Wherever you round a result to a currency's smallest unit (or to the tenth of a percent), round half to even (banker's rounding) instead of half up: when the value is exactly halfway, the result is the neighbouring even number. 0.5 becomes 0, 1.5 becomes 2, 2.5 becomes 2, -2.5 becomes -2; a percentage of 0.25 becomes 0.2 and 0.35 becomes 0.4. This is `round_div` and so everything that uses it: converting an amount between currencies (`RateTable.convert`, the converted reports, `calc money convert`), multiplying an amount by a ratio (`Money.scale`, `calc money scale`), the part of a budget that falls in a period (the prorated allowance), the "percent used" of a budget (one decimal), and the percentages in the reports. Dividing an amount among parts (`allocate`, largest remainder) does not change.

## 2. A lock date

I want to close a period so that nobody, me included, can change it by accident. The book can have a lock date. A transaction dated on or before the lock date can no longer be added, deleted, imported, or created by the recurring entries. The operation is refused with the error code `locked` and **nothing at all is changed**: an import that contains one locked row adds none of its rows, a journal import adds none of its accounts, rates or transactions, and a refused `materialize` does not move any series forward. Nothing else is affected (accounts, rates, budgets, rules, reports, closing an account).

- **Library.** `tallybook.errors.LockedPeriodError` is a kind of `ConflictError` with the code `locked`; its message contains the word `locked`. `Store.set_lock(day)` sets the lock to a date (it may be moved earlier or later), `Store.set_lock(None)` removes it, `Store.lock_date()` returns the date or `None`; the lock is kept in the book file. `Ledger` has an attribute `lock_date` (`None` by default; I may assign it) that is honoured by `Ledger.add`, `Ledger.add_many` (all or nothing), `Ledger.remove` (by the date of the transaction removed) and `Ledger.replace` (refused if the old or the new date is locked). `Store.ledger()` returns a ledger whose `lock_date` is the store's. `Store.add_transaction`, `add_transactions`, `delete_transaction`, `import_csv`, `load_journal` and `materialize` raise `LockedPeriodError` for a locked date.
- **Command line.** `tallybook lock show` prints the lock date as `YYYY-MM-DD`, or `none`; `tallybook lock set 2024-03-31` prints `locked through 2024-03-31` and `tallybook lock clear` prints `lock cleared` (also when there is no lock); all exit 0. A malformed date is exit 1; a missing or surplus argument, or `lock` alone, exit 2. Any refused operation (`tx add`, `tx delete`, `journal import`, `import`, `recurring materialize`) is exit 1 with the usual `tallybook: <message>` on standard error and nothing on standard output. Before this change `lock` is an unknown command (exit 2).
- **HTTP API.** `GET /lock` answers 200 `{"lock_date": "2024-03-31"}`, or `{"lock_date": null}` when there is no lock. `PUT /lock` with the same body sets it, and `{"lock_date": null}` removes it; it answers 200 with the same shape showing the lock now in force. The field `lock_date` must be present (`{}` is an error) and nothing else may be sent; a date that is not `YYYY-MM-DD` is a parse error and a value that is neither text nor `null` a validation error (statuses below). `POST` or `DELETE` on `/lock` is 405 with `Allow: GET, PUT`. A refused operation (`POST /transactions`, `DELETE /transactions/<id>`, `POST /import`, `POST /recurring/materialize`) answers 409 with the code `locked`. Before this change `/lock` is a 404 like any unknown path.

## 3. The API's error body

An error answer from the HTTP API has the body `{"error": {"code": "<code>", "message": "<text>"}}` instead of `{"error": "<text>"}`. The `code` is the error's code (`parse`, `validation`, `not_found`, `conflict`, `locked`), which includes an unknown path (`not_found`); for a request the server turns away before it gets to any of that it is `bad_request` (an unreadable request line or a `Content-Length` that is not a number: status 400), `method_not_allowed` (405), `unsupported_media_type` (415) or `too_large` (413); a failure of the server's own is `internal` (500). Errors in what I sent (invalid JSON, a value that does not parse or fails a rule: codes `parse` and `validation`) answer **422** instead of 400. Every other status stays as it is.
