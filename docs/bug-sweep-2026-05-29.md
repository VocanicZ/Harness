## ✅ DONE — PR #103 (OPEN, MERGEABLE)
https://github.com/VocanicZ/Harness/pull/103 · no auto-merge (repo policy) → squash at review.

- **#1/#2/#3 — gh failures read as "empty repo"** (`scripts/issuelib.py`). Introduced a
  `GhError` seam: a positively-identified transient gh failure (rate-limit/403/429/5xx/
  network, matched from stderr) raises → CLI prints nothing, exits non-zero → worker HOLDS
  the tick. Kills the spurious `PLAN` re-fire and the poller snapshot-clobber. Legitimately
  empty (`gh issue list` exit 0 `[]`) / absent (non-transient non-zero, e.g. 404) unchanged.
- **#4 — fd-9 leak on poller spawn** (`scripts/lib.sh` `ensure_poller`). Spawns the
  never-killed poller with `9>&-` so it can't inherit start.sh's start-lock and wedge a
  later `start --recover` into launching zero workers.
- Tests: 4 new gh-error cases in `test_issuelib.py` (+ subprocess-level dispatch-holds
  check) and new `test/test_poller_fd9.sh`. Full suite green (38/38).

## 📋 QUEUED — inject-ready briefs (feed each to `/harness-issue`)

All target the engine repo (VocanicZ/Harness), bug-lane, test-first. Keep the #103
`GhError` semantics intact in anything touching `issuelib.py`.

### Brief 1 — `gh issue list` silently truncates at 200 (no pagination)
- **File:** `scripts/issuelib.py:147` (`_fetch_issues`)
- **Problem:** `gh issue list --state all --limit 200` — on a large/old repo the PRD or an
  open ready child can fall past 200 and vanish from `compute_state` (missing PRD flips
  `prd_open`/`children_exist`; missing open child drops from `unblocked` or lets the unit
  read complete). No warning when the cap is hit.
- **Fix:** Paginate the fetch (prefer `gh api --paginate` on the issues endpoint, or loop
  pages) so all matching issues are retrieved. At minimum, detect cap-hit and log a loud
  stderr warning + raise the cap. A mid-pagination failure must raise `GhError` (hold), not
  read as "fewer issues".
- **Acceptance (`test_issuelib.py`):** faked `gh` returning >200 issues across pages →
  PRD and an open child beyond #200 both present in `compute_state`; empty/short repo
  unchanged; cap-hit (if any remains) logs a visible warning.

### Brief 2 — `uninstall` can `rm -rf` a non-`.harness` `STATE_DIR`
- **File:** `scripts/uninstall.sh:70-76` (`remove_project_state`)
- **Problem:** Only guard before `rm -rf "$STATE_DIR"` is `[[ -n "$STATE_DIR" ]]`; a pre-set
  env `STATE_DIR` is honoured verbatim. `migrate.sh` already gates on a `config` marker.
- **Fix:** Before delete, require `STATE_DIR` to end in `*/.harness` AND contain a `config`
  marker (mirror `migrate.sh`); on mismatch refuse + explain. Normal discovered-`.harness`
  case unchanged.
- **Acceptance (`test_uninstall.sh`):** `STATE_DIR` not ending in `/.harness` (or lacking
  `config`) deletes nothing; normal `.../.harness` still removed.

### Brief 3 — `remove_skills` can expand to literal `/harness` when `HARNESS_USER_SKILLS` empty
- **File:** `scripts/uninstall.sh:79-84` (`remove_skills`)
- **Problem:** `${...:-default}` only guards *unset*; an exported empty value makes the loop
  expand `"$HARNESS_USER_SKILLS"/harness` → `/harness`. `[[ -e ]]` bounds it but it's an
  unguarded absolute target from string concat.
- **Fix:** `[[ -n "$HARNESS_USER_SKILLS" && -d "$HARNESS_USER_SKILLS" ]] || return 0` before
  the loop.
- **Acceptance (`test_uninstall.sh`):** exported-empty → no-op, never references `/harness`;
  populated dir → `harness` + `harness-*` still removed.

### Brief 4 — `bug-triage.md` close path omits `--remove-label`
- **File:** `prompts/bug-triage.md:31-37`
- **Problem:** Prose (~L32) says remove `{{LABEL_WORKING}}` on close; command block (~L36-37)
  only `gh issue comment` + `gh issue close`. Closed invalid/dup/wontfix bugs keep
  `agent-working`. Harmless to dispatch, but self-contradictory.
- **Fix:** Add `--remove-label {{LABEL_WORKING}}` to the close command.
- **Acceptance:** template consistent; assert in `test_prompt_labels.sh` if applicable.

### Brief 5 — Guard `launch_claude` against re-dispatch into a live session (#6, defensive half)
- **Files:** `scripts/lib.sh` `launch_claude` (~567-580); callers in `scripts/drive.sh`
  (`spawn_impl`/`spawn_orch`/`spawn_bug`)
- **Problem:** Spawn paths `tmux new-session -d -s "$sess"` then `send-keys "exec claude …"`
  with no `session_live` check. If the same issue is re-selected while its session is live,
  `new-session` fails on the dup name (ignored) and `send-keys` injects into the running
  agent's pane. (Root cause — dropped `agent-working` under rate limit — largely mitigated
  by #103's hold-on-transient-error; this is the belt-and-suspenders guard.)
- **Fix:** Make the spawn a no-op when the target session is already live (`session_live` →
  log + return). Scope strictly to "never send-keys into an existing session."
- **Acceptance (`test_spawn.sh`/`test_worker.sh`):** spawn against a live session does not
  send-keys / does not error; fresh session still spawns.
- **Depends on:** #103 merge (shared root cause).

## 🧭 DESIGN-FIRST — needs an approach decision (route via `/harness-prd` or `/harness-plan`)

Do **not** hand these to an autonomous agent as a blank "fix the race" — pick the approach
first, then implement.

### D1 — Shared-checkout `.harness-task.md` clobber (#5)
- **Files:** `scripts/lib.sh` (`launch_claude` ~567-580, `bug_checkout`/`unit_checkout`),
  `scripts/drive.sh:138/148/172/223`, `scripts/inject.sh:57`
- **Problem:** `bug_checkout()` and `unit_checkout()` resolve to the **same** directory. A
  bug-triage session is not counted by the pool's orch-gate, so a triage and an
  orchestration session can co-run against one checkout. The second `render >
  .harness-task.md` overwrites the first agent's brief during its
  `send-keys "...$(cat .harness-task.md)"` launch window, and `spawn_orch`'s
  `git reset --hard origin/<base>` + `git checkout` yanks files out from under the triage
  session reading code in the same checkout.
- **Approaches to decide between:**
  1. **Per-session checkout** — each spawn gets its own worktree/checkout (clean isolation;
     more disk + worktree lifecycle to manage).
  2. **Gate triage vs orchestration** — make `count_team_sessions` (or the orch-gate) aware
     of bug sessions so they can't co-run with orchestration on the shared checkout (less
     disk; reduces concurrency; bug lane is cap-1 so impact may be acceptable).
  3. **Atomic brief handoff** — pass the brief via a unique per-session path / arg instead
     of a shared `.harness-task.md`, and stop `cat`-ing at send-keys time.
- **Open question:** is the bug lane's independence from the pool worth preserving, or is
  per-session isolation simpler overall? Lean toward (1) or (3); (2) couples the lanes.

### D2 — Re-dispatch root cause / claim atomicity (#6 root)
- **Files:** `scripts/drive.sh:155` (`agent-working` stamp `|| true`), `issuelib.py:339-343`
  (`unblocked` selects on absence of `agent-working`), `scripts/lib.sh` claim path
- **Problem:** IMPL claim is non-atomic: `dispatch` selects by absence of `agent-working`,
  the stamp happens later in bash and swallows failures. Two near-simultaneous pool ticks
  can both select the same issue before either label write lands. #103 reduces the
  rate-limit-drop window (transient errors now hold), and Brief 5 stops the worst symptom
  (send-keys into a live pane), but the underlying TOCTOU remains.
- **Approaches to decide between:**
  1. **Compare-and-set claim** — make the claim atomic (e.g. claim-file lock keyed by issue
     number taken before/around the label write; reject if already claimed).
  2. **Verify-after-stamp** — re-read the label after stamping and abort the spawn if a peer
     won the race.
  3. **Lean on Brief 5 + #103** and accept the narrowed window as good-enough (cheapest;
     document the residual race).
- **Open question:** how much concurrency does the pool actually run per repo? If CAP is
  small and Brief 5 lands, (3) may suffice; otherwise (1).
